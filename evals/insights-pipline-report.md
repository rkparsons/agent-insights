## Recommendations

- `[claude_md_rule]` Verify diagnoses and factual claims against real evidence — search, server logs, real Redis/production data, origin/develop — before asserting a conclusion, actively look for evidence that contradicts your first hypothesis, and account for context the user already provided. (evidence: 8 sessions)
- `[claude_md_rule]` Keep changes tightly scoped to what was asked — no incidental refactors, doc bundling, or memory-bookkeeping — and don't take outward-facing actions (push, open a PR) unless explicitly requested; leave the branch for the user's manual verification. (evidence: 9 sessions)
- `[claude_md_rule]` Match process weight to the task: for small or exploratory work, engage directly instead of front-loading parallel Explore agents, extended solo exploration before asking the user's questions, or a full TDD ceremony for a trivial change. (evidence: 4 sessions)
- `[claude_md_rule]` Validate the ticket/spec and its scope before implementing rather than following it blindly, and keep specs at design altitude — final-state understanding with unknowns flagged, no overturned history or implementation detail that belongs in planning. (evidence: 5 sessions)

## Already in place (reinforce?)

## Top friction themes

1. **AskUserQuestion forced-choice used where the user wanted to talk it through** — 27 incidents across 26 sessions. Across many sessions Claude reached for the AskUserQuestion multiple-choice widget on decisions the user wanted to discuss, and offered options that were incomplete, convoluted, missing context, or lacked a recommendation, so the user repeatedly rejected the question to clarify or reframe in their own words.
2. **Long unsystematic debugging without a reproducing red test first** — 20 incidents across 9 sessions. Debugging sessions ran long and unsystematically — jumping between hypotheses, relying on brittle live running sessions, shipping fixes for the wrong root cause, and looping on repro requests — instead of first pinning the bug with a deterministic reproducing red test.
3. **Declared done and verified, then broke the moment the user ran it live** — 19 incidents across 14 sessions. Features were repeatedly declared done and verified on green headless tests and passing reviews, then failed the instant the user ran them in the real terminal — freezing the app, not firing keybindings, still flickering or corrupting, or missing padding — because the automated verification never exercised the live tmux/Ghostty rendering path.
4. **Dropping or silently changing stated inputs and existing behavior** — 10 incidents across 7 sessions. Claude silently replaced or dropped things the user had specified or that already existed — a color pill, a folded card, state-aware toggle behavior, worktree padding, an already-dropped weather concept — or misread the request's intent, ignoring stated inputs rather than preserving them and flagging changes.
5. **Confident but wrong claims surviving unverified into deliverables** — 9 incidents across 8 sessions. Claude stated technical conclusions confidently but wrongly — a real hook called nonexistent, an unreachable guard read as reachable, a spec comparing values equal by construction, glyph widths and design constraints asserted without checking — and these survived into specs, reports, and fixes until the user challenged them.
6. **Simple mechanical tasks over-scoped into heavy design exploration** — 8 incidents across 8 sessions. Simple mechanical asks — repositioning a panel, tuning exact row/padding numbers, printing options, a trivial visual tweak, running a command — were inflated into open-ended design exploration with brainstorming and mockups, forcing the user to redirect Claude back to just doing the small thing.
7. **Specs and designs shipped on false premises, underscoping, or thin research** — 8 incidents across 7 sessions. Initial specs and designs shipped with false premises, underscoping, reuse-leaning hedges, latent hardcoded assumptions, and incomplete prior-art research, and were only corrected when the user demanded an adversarial review or pointed out the missing option.
8. **Acting on the wrong or unsafe target in the real environment** — 6 incidents across 5 sessions. Claude acted against the wrong or unsafe target in the real environment — editing and testing in the main worktree instead of the feature worktree, omitting the required cd, running parallel agents on a shared worktree that hard-reset the branch, mismodeling the session topology, and attempting non-terminating or mass-destructive operations on the user's real store.
9. **Cleanup and commit discipline lapses** — 6 incidents across 6 sessions. Cleanup and commit discipline lapsed — throwaway test files and discovery docs left behind, a change committed without running tests, and comments tightly coupled to constants or over-restored against the user's lean-toward-removal intent.
10. **Terminal decisions driven by mockups that misrepresent real rendering** — 5 incidents across 5 sessions. ## Workflow opportunities

- **Heavy sessions burn effort re-reading files to rebuild context** (14 sessions). The heaviest design, refactor, and debugging sessions spend a large share of effort re-reading the same files to rebuild context, pointing to an opportunity to front-load understanding, delegate broad reading to summarizing subagents, and keep a persistent codebase map.
- **The design-to-build pipeline works but ends with live behavior unverified** (13 sessions). The dominant successful pattern is a repeatable pipeline — brainstorm, spec, adversarial review, plan, subagent-driven TDD, then leave the branch for manual test — that delivers merge-ready work, but it almost always ends with the visual and live behavior unverified, so the durable gap worth closing is a built-in live-verification step for TUI work.
- **Friction concentrates in probe sessions and long live-debugging loops** (5 sessions). Friction concentrates in exploratory probe sessions and long live-debugging loops; the debugging loops in particular repeatedly stall for want of an upfront deterministic reproduction, which is the highest-leverage place to change the workflow.

## Recommendations

- `[claude_md_rule]` When a decision is open-ended, subjective, or a design judgment, discuss it conversationally instead of forcing an AskUserQuestion multiple-choice widget; reserve the widget for genuinely discrete choices, and when you use it always lead with your recommendation and make the options complete and self-explanatory. (evidence: 6 sessions)
- `[claude_md_rule]` Never claim a TUI or terminal change is done, verified, or ready on the strength of green headless tests and code reviews alone — confirm the behavior in the real terminal/tmux app first; when only the user can run it live, say so explicitly and leave the branch for their manual test rather than asserting success. (evidence: 7 sessions)
- `[claude_md_rule]` For any bug, reproduce it with a deterministic failing red test before attempting a fix, and debug systematically rather than jumping between hypotheses or open-ended live-forensics; before asking the user to repeat a capture or repro step, explain how this attempt differs from what already failed. (evidence: 3 sessions)
- `[claude_md_rule]` Do not assert a technical claim — that a hook or API exists, a code path is reachable, two values differ, or a glyph is a given width — without backing it with a concrete check against the actual code or environment; verify before the claim enters a spec, report, or fix. (evidence: 6 sessions)
- `[new_skill]` Build a skill that previews candidate glyphs, colors, and layouts by rendering them in the real target terminal (tmux/Ghostty) and capturing a screenshot, so terminal-fidelity decisions never rely on browser mockups or plain captured ANSI, which misrepresent real rendering. (evidence: 4 sessions)
- `[claude_md_rule]` Match effort to the request: treat positional, numeric, and mechanical changes as such and implement them directly instead of opening brainstorming, mockups, or exploration; and when given an explicit 'do exactly X and nothing else' command, run it verbatim without hedging or clarifying questions. (evidence: 6 sessions)
- `[claude_md_rule]` Never silently drop or change anything the user specified or an existing behavior or convention (padding, status color, state-aware labels); preserve stated inputs, honor established spacing conventions, and flag any deviation for discussion before acting on it. (evidence: 7 sessions)
- `[claude_md_rule]` Confirm you are acting on the intended target before editing, building, or testing — verify the working directory and that changes land in the feature worktree, not main; isolate parallel subagents in separate worktrees; and never run bulk or destructive operations against the user's real repo or data store. (evidence: 5 sessions)
- `[claude_md_rule]` Before implementing any spec or plan, dispatch the most capable subagent to run an adversarial review hunting for false premises, gaps, and mistakes (not implementation detail), validate each finding against the actual code, fold in only the valid ones, and re-run the same review after every rewrite until it holds. (evidence: 9 sessions)
- `[claude_md_rule]` Clean up as you go: when a change lands or a feature is removed, delete the dead code and now-obsolete plumbing, remove leftover discovery docs and throwaway test files, and never commit without first running the tests. (evidence: 7 sessions)
- `[claude_md_rule]` Before designing, research how leading tools solve the problem and identify the gold-standard pattern, prefer solutions that don't depend on the developer's personal cloud or account, and finish that research before moving into design. (evidence: 3 sessions)
- `[setting]` Add settings guardrails so irreversible operations require confirmation — put `git reset --hard` and bulk `rm` under `~/.claude/projects` on an ask-or-deny list — to prevent subagents from wiping branches or the transcript store. (evidence: 2 sessions)
- `[habit]` For large design, refactor, or debugging work, front-load understanding of the existing system and delegate broad reading to Explore subagents that return summaries, and keep a persistent codebase map, so sessions don't burn effort re-reading the same files to rebuild context. (evidence: 2 sessions)

## Already in place (reinforce?)

- `[claude_md_rule]` When work is complete, don't commit, merge, or open a PR unless the user explicitly asks — leave the branch as-is for their manual testing.
